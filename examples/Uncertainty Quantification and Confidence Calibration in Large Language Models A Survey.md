## 核心问题——LLM 输出不可靠，但不知道什么时候不可靠

- LLM 在医疗、法律等高风险场景广泛使用
- 研究显示医疗问答任务中 **超过 30%** 的回答含事实错误
- 传统不确定性量化方法（贝叶斯方法、集成方法）对 LLM 不适用
  - 参数量太大，多次前向传播成本过高
  - 解码策略多样，一致性难保证
- **LLM 引入了传统机器学习没有的不确定性来源**

## 传统方法为什么在 LLM 上失效？

<div class=ldiv>

**贝叶斯方法** 对权重建后验分布（如 MC Dropout），需要多次前向传播

**集成方法** 训练多个模型聚合预测，成本是单模型的 N 倍

> 两类方法在小模型上有效，但 LLM 的参数规模（百亿-万亿级）让多次前向传播变得不现实。

</div>

<div class=rdiv>

| 维度 | 传统方法假设 | LLM 实际情况 |
|------|------------|------------|
| **参数规模** | 传统 ML 模型 | 百亿-万亿级，多次前向传播成本过高 |
| **解码过程** | 确定性映射 | 采样策略多样（top-k, nucleus），输出随机 |
| **不确定性来源** | 偶然 + 认知二分 | + 输入歧义、推理链误差、知识缺口 |
| **访问方式** | 通常可访问权重 | 多数 API 是黑盒 |

> **核心矛盾** 贝叶斯和集成方法的计算成本不可承受；传统二分法覆盖不了 LLM 特有的不确定性来源

</div>

## 四维度框架如何解耦 LLM 特有不确定性来源？

| 维度 | 不确定性类型 | 来源 | 举例 |
|------|-------------|------|------|
| **输入不确定性** | 偶然不确定性 | 输入歧义/不完整 | "这个国家的首都是？"缺上下文 |
| **推理不确定性** | 混合 | 多步推理中误差累积 | 推理链中某步出错导致后续全偏 |
| **参数不确定性** | 认知不确定性 | 训练数据缺口 | 未见过的知识产生幻觉 |
| **预测不确定性** | 混合 | 多次采样输出不一致 | 同一问题多次回答不同 |

<!--

[照读] 论文把 LLM 的不确定性分成四个维度：输入不确定性来自歧义，推理不确定性来自误差累积，参数不确定性来自训练数据缺口，预测不确定性来自多次采样不一致。其中推理和预测是混合型，同时包含偶然和认知两种成分。

**模型访问** 白盒 = 能看到模型内部（权重、隐藏状态）/ 黑盒 = 只能调 API

| CoT-UQ | 推理 | 单轮 | 白盒 |
| BLoB | 参数 | 微调 | 白盒 |
| 语义熵 | 预测 | 多轮+附加模型 | 白盒 |

## 输入歧义是纯粹偶然不确定性

**问题** 输入歧义导致多种合理回答

| 方法 | 做法 | 效率 |
|------|------|------|
| Input Clarification Ensembles | 生成多个澄清版本，用互信息衡量分歧 | 多轮 |
| ICL-Sample | 用不同上下文学习样本量化输入敏感度 | 多轮 |
| SPUQ | 对输入做同义改写/加噪声，用 BERTScore 衡量一致性 | 多轮+附加模型 |

> 输入不确定性是纯粹的偶然不确定性，即使完美模型也无法消除歧义。

<!--
[1.5 min] 输入不确定性：核心是"同一个问题，不同问法得到不同答案"。
三种方法都依赖多轮采样——因为要衡量输入变化对输出的影响，必须多次变换输入才能检测一致性。
单轮方法无法量化输入不确定性（只看一次输出不知道换个问法会不会变）。
重点讲 SPUQ——它最直观（改写输入看输出变不变），适合做 demo 说明。

[照读] 输入不确定性关注的是同一个问题换个问法答案会不会变。三种方法都是对输入做变换然后看输出一致性。之所以都是多轮，是因为必须多次变换输入才能衡量一致性——单轮方法做不到。SPUQ 最直观——对输入做同义改写或加噪声，用 BERTScore 衡量输出变了多少。

## 推理链误差累积——如何实时监控中间步骤？

**问题** 多步推理中误差累积，中间步骤的不确定性如何量化？

| 方法 | 做法 | 特点 |
|------|------|------|
| CoT-UQ | 把思维链推理整合进 UQ 框架 | 单轮，可同时给置信度 |
| TopologyUQ | 把 LLM 解释提取为图结构，用图编辑距离量化 | 可解释性强 |
| TouT | 思维树 + 蒙特卡洛 Dropout 给决策点打分 | 引导推理探索 |
| **UAG** | 监控每步词元概率，高不确定时回退到可靠状态 | <span style="background:rgba(74,144,217,0.18);border-radius:4px;padding:2px 6px;">减少误差累积</span> |

<br>

> 推理不确定性是混合型
问题本身模糊时属于偶然不确定性，模型推理不稳定时属于认知不确定性。

<!--

[照读] 推理不确定性关注推理链中哪一步可能出错。四种方法：CoT-UQ 把思维链整合进 UQ，TopologyUQ 用图结构量化，TouT 用思维树加 MC Dropout，UAG 最实用——它能实时监控每步的不确定性，发现不确定时回退到可靠状态。

[记住] 推理不确定性的核心挑战 = 如何实时监控中间步骤的可靠性。UAG 是最实用的方案。

## 参数不确定性可通过训练减少

**问题** 训练数据缺口导致模型对自身预测不确定

| 方法 | 做法 | 访问级别 |
|------|------|----------|
| BLoB / BLoRA | 在 LoRA 适配器中引入贝叶斯建模 | 白盒 |
| SAPLMA | 动态调整概率对齐的不确定性估计 | 白盒 |
| UaIT | 微调时显式训练模型表达不确定性 | 白盒 |
| **LoRA Ensembles** | 训练多个轻量 LoRA 变体代替全模型集成 | <span style="background:rgba(74,144,217,0.18);border-radius:4px;padding:2px 6px;">白盒</span> |

<br>

## 预测不确定性——最直观的 UQ 方式

**问题** 如何在一次生成中估计输出的不确定性？

前三个维度（输入、推理、参数）关注的是"不确定性从哪来"。
预测不确定性关注的是"怎么衡量"——这是最直接的 UQ 方式，也是大多数现有方法的焦点。

| 指标 | 公式思路 | 含义 |
|------|---------|------|
| 困惑度 Perplexity | $\exp(-\frac{1}{N}\sum \ln p(w_i))$ | 越高 = 越不确定 |
| 熵 | $-\sum p(w)\log p(w)$ | 概率分布的分散度 |
| P(True) | 问 LLM 自己"这个回答对吗？" | 自我评估 |

**单次生成** 只看一次输出，成本低，但信息量有限
无法判断不确定性是否可靠。正因如此，需要多次采样通过输出一致性来获得更可靠的估计。

<!--
[2 min] 前面三个维度讲的是"不确定性从哪来"，现在第四个维度预测不确定性讲的是"怎么衡量"。
这是最直观的 UQ 方式——直接看模型输出的概率分布。
Perplexity 和熵是最基础的指标，P(True) 最有趣（让模型自我评估）。

困惑度公式 $\exp(-\frac{1}{N}\sum \ln p(w_i))$ 逐项分解：
  - $p(w_i)$: 模型对第 i 个 token 的预测概率（softmax 输出）
  - $\ln p(w_i)$: 取对数，将概率转为"信息量"——概率越高，负对数越小（越不"惊讶"）
  - $\sum \ln p(w_i)$: 所有 token 的对数概率之和（即 log-likelihood）
  - $-\frac{1}{N}$: 取负并求平均 → 得到平均负对数似然（也就是交叉熵 H）

  每步平均在 10 个等概率候选中选择。越低 = 模型越"确定"。

  对应原始空间的几何平均。

## AUROC 和 AUARC：怎么判断"分离效果好不好"？

<div class=ldiv>

**AUROC** — 能分开"对"和"错"吗？

按不确定性分数排序，逐步提高阈值，画 ROC 曲线
- **面积越大 = 分离能力越强**
- 随机猜测 = 0.5，完美分离 = 1.0

</div>
<div class=rdiv>

**AUARC** — 拒绝后准确率提升多少？

按不确定性排序，逐步拒绝最不确定的回答，画准确率曲线
- 如：拒绝 30% → 准确率 70% → 92%
- **面积越大 = 拒绝策略越有效**

</div>

> AUROC 衡量"区分力"，AUARC 衡量"拒绝价值"。两者互补：AUROC 高不代表 AUARC 高。

<!--

[1.5 min] 承接上页的评估流水线，现在讲两个核心指标怎么解读。
左栏 AUROC：核心是"分离能力"。用一个直觉——把回答按不确定性从低到高排，看排在前面的是否真的是"对的"。AUROC 就是衡量这个排序有多好。

## 下一步值得关注的方向——Agent 不确定性会沿决策链传递放大

考虑一个**安全评估 Agent** 的典型推理链：

<div style="background:rgba(232,168,56,0.12);border-radius:8px;padding:10px 14px;text-align:center;font-size:0.85em;min-width:100px;">
<b>解析结果</b><br>不确定性 0.4

<div style="font-size:1.3em;color:#dc3232;">→</div>

第 2 步误判服务版本 → 后续 CVE 匹配全部偏移 → 修复建议完全错误。每步的不确定性向下游累积，而论文指出 “LLM 做出一个判断后，即使后续收到了与之前判断矛盾的新信息，它也倾向于坚持原来的判断，不会主动回退修正”[14]

**例子** Agent 在第 2 步判断目标服务是 Apache 2.4.49 → 基于这个判断去匹配 CVE → 在后续扫描中发现了明显属于 Nginx 的特征 → 但 Agent 继续沿着 Apache 的路径往下走

## 现有框架为什么不够

<div style="display: flex; gap: 20px; margin-top: 8px;">
<div style="flex: 1; background: rgba(220,50,50,0.06); border-radius: 8px; padding: 12px 14px;">

### 为什么不够？

论文的四维度框架（输入·推理·参数·预测）是对**单次任务输出**的不确定性分类。30 多种方法中很多是多轮采样的（语义熵、SPUQ 等），但它们的"多轮"是为了**更准确地估计同一次输出的不确定性**

- 输入不确定性：一次提问的歧义
- 推理不确定性：一次推理链的误差累积
- 参数不确定性：模型自身知识缺口
- 预测不确定性：一次输出的不一致

</div>
<div style="flex: 1; background: rgba(74,144,217,0.06); border-radius: 8px; padding: 12px 14px;">


<div style="background:rgba(74,144,217,0.1);border-radius:6px;padding:8px 12px;margin-bottom:8px;font-size:0.9em;">

**① 置信度门槛** Agent 应在何时暂停行动？
高风险工具调用（如修改配置）前，需要不确定性检查点

</div>
<div style="background:rgba(123,104,238,0.1);border-radius:6px;padding:8px 12px;margin-bottom:8px;font-size:0.9em;">

**② 自我反思** Agent 能否在发现矛盾时回头修正？
论文指出 LLM 往往不会修正早期决策 [14]，需要显式的反思-回退机制

</div>

论文建议用 graph-based representations [74, 125] 追踪不确定步骤

## 如果把 Agent 的动作链画成图，UQ 可以做到更精确

Agent 的推理链是一张 **有向无环图**。每个节点是一次动作，边是依赖关系
不确定性沿边传递——上游的误判会放大到下游

<div style="display:flex;gap:28px;align-items:flex-start;margin-top:4px;">
<div style="flex:0 0 32%;">

```text
       ┌───────────────────┐
       │    理解目标        │
       │     U = 0.1       │
       └───┬───────────┬───┘
           │           │
           ▼           ▼
  ┌──────────────┐  ┌──────────┐
  │  nmap 扫描   │  │ whois    │
  │   U = 0.2    │  │  U = 0.1 │
  └──────┬───────┘  └────┬─────┘
         │               │
         ▼               ▼
  ┌──────────────────────────┐
  │   服务版本识别  ◀瓶颈     │
  └─────────────┬────────────┘
                ▼
        ┌───────────────┐
        │  CVE 匹配     │
        │    U = 0.7    │
        └───────────────┘
```

</div>
<div style="flex:1;font-size:0.88em;">

**瓶颈节点 = 上游不确定性高 × 下游依赖多**

服务版本识别是瓶颈：上游 nmap 结果不确定（端口可能被过滤），下游 CVE 匹配和修复建议全部依赖它。一个小误判在这里会放大 3-4 倍。

- 先算出每个节点的不确定性贡献
- 只在瓶颈节点做**重点验证**（如语义熵多次采样）
- 不确定性仍超阈值 → **分叉探索**（换工具/换路径）


</div>
</div>
